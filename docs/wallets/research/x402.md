# x402 research (as of 2026-11-23)

## Summary

x402 is an HTTP payment protocol: a server answers `402 Payment Required` with the payment terms, the client signs a payment and retries, and a facilitator verifies and settles it. The EVM `exact` scheme carries an EIP-3009 `transferWithAuthorization` signature, so the payer signs a USDC transfer and never sends a transaction. Two generations are live. v1 (the `x402` npm package, 1.2.0) uses `X-PAYMENT` and `X-PAYMENT-RESPONSE`. v2 (the `@x402/*` family, 2.32.0, released 2026-11-20) uses `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE` and `PAYMENT-RESPONSE`, and CAIP-2 network ids. The two official repos are `x402-foundation/x402` (active, 6,822 stars, pushed 2026-11-23) and `coinbase/x402` (186 stars, pushed 2026-11-19); the npm metadata for `@coinbase/x402` is stale.

Three facts matter most for banda:
1. The USDC EIP-712 domain `name` differs by chain: Base mainnet reports `"USD Coin"`, Base Sepolia reports `"USDC"`. The spec example uses `"USDC"`. Hard-coding one value gives a signature that fails on the other chain.
2. The spec and the security literature say the client must not trust the 402 challenge blindly. The arXiv study (May 2026) reports cross-resource substitution and facilitator-trust failures in the official SDKs.
3. x402 settlement is the facilitator's transaction, so the facilitator pays gas and can be a censorship or availability point. Replay protection is the EIP-3009 nonce, not anything in the HTTP layer.

## Findings with sources

### Protocol and versions
- v1 spec (`specs/x402-specification-v1.md`): `x402Version` 1. 402 body: `x402Version`, `error`, `accepts`. PaymentRequirements: `scheme`, `network`, `maxAmountRequired`, `resource`, `description`, `mimeType` (optional), `payTo`, `maxTimeoutSeconds`, `asset`, `extra` (optional), `outputSchema` (optional). Network ids are names: `base`, `base-sepolia`. Source: https://github.com/coinbase/x402/blob/main/specs/x402-specification-v1.md (fetched 2026-11-23; the spec file also exists at the `x402-foundation/x402` path).
- v1 headers: `X-PAYMENT` (client to server, retry) and `X-PAYMENT-RESPONSE` (server to client). The v1 spec names `X-PAYMENT` only in an example error string and does not define `X-PAYMENT-RESPONSE` precisely ("the payment response field"). Treat the v1 header set as lightly specified.
- v2 spec (`specs/x402-specification-v2.md`): `x402Version` 2. PaymentRequired: `x402Version`, `error` (optional), `resource`, `accepts`, `extensions` (optional). PaymentRequirements: `scheme`, `network` (CAIP-2, e.g. `eip155:84532`), `amount` (atomic units, replaces `maxAmountRequired`), `asset`, `payTo`, `maxTimeoutSeconds`, `extra`. PaymentPayload: `x402Version`, `resource` (optional), `accepted`, `payload`, `extensions` (optional). Source: same repo, `specs/x402-specification-v2.md`.
- v2 HTTP transport (`specs/transports-v2/http.md`): `PAYMENT-REQUIRED` (server to client, base64 PaymentRequired), `PAYMENT-SIGNATURE` (client to server, base64 PaymentPayload), `PAYMENT-RESPONSE` (server to client, base64 SettlementResponse). Status: 402 for payment required, and 402 with `PAYMENT-RESPONSE` `success:false` plus `errorReason` on settlement or verification failure; 400 for malformed payload; 500 for internal error; 200 on verified and settled. The client should send back the `accepted` entry it chose. Source: https://raw.githubusercontent.com/coinbase/x402/main/specs/transports-v2/http.md (fetched 2026-11-23).
- The docs site (https://docs.x402.org/core-concepts/http-402) confirmed the three v2 headers, all base64 JSON. Its page does not state the body fields.

### Exact scheme on EVM
- Spec: `specs/schemes/exact/scheme_exact_evm.md`. Payload: `signature` and `authorization` (`from`, `to`, `value`, `validAfter`, `validBefore`, `nonce`). The `extra` object in PaymentRequirements carries the token's EIP-712 `name` and `version`. Example uses `network: "eip155:84532"`.
- Facilitator verification, in order (per the scheme doc): (1) signature recovers to `from`; (2) payer balance covers the asset; (3) amount and validity window meet the requirement; (4) token and network match; (5) simulate `transferWithAuthorization`. Settlement calls `transferWithAuthorization` with the signature and authorization. If the broadcast succeeds but confirmation is not established, the facilitator may return `settlement_pending` with the tx hash.
- The scheme doc does not list security considerations for the EIP-3009 path. The only security list in the page is for the ERC-7710 delegation section (client revocation race, malicious delegation manager gas). Source: https://raw.githubusercontent.com/coinbase/x402/main/specs/schemes/exact/scheme_exact_evm.md (fetched 2026-11-23).

### EIP-3009 (typed data)
- Spec: https://eips.ethereum.org/EIPS/eip-3009 (Draft, Standards Track: ERC; created 2020-09-28; authors Peter Jihoon Kim, Kevin Britz, David Knott). Fetched 2026-11-23.
- TransferWithAuthorization type string: `TransferWithAuthorization(address from,address to,uint256 value,uint256 validAfter,uint256 validBefore,bytes32 nonce)`. Typehash `0x7c7c6cdb67a18743f49ec6fa9b35f50d52ed05cbed4cc592e13b44501c1a2267` (quoted from the EIP page).
- Domain: `EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)` is the recommended shape; the contract chooses the fields, and `verifyingContract` plus `chainId` are strongly recommended to bind signatures to one token on one network.
- `validAfter` and `validBefore` are Unix times, checked with strict comparisons. `nonce` is a random 32-byte value, unique per authorizer, stored in a mapping, and single-use.
- `receiveWithAuthorization` exists with the same fields and a separate typehash (`ReceiveWithAuthorization(...)`). It requires `msg.sender == to`, which prevents a third party from front-running a wrapper contract by submitting the authorization directly. The x402 exact scheme uses `transferWithAuthorization`, so a payee must be the `to` address of the transfer, and the front-running window is the reason the spec exists; it does not affect banda's own design because banda is the payer.

### USDC contracts and EIP-712 domain (verified on-chain, read-only)
- Base mainnet USDC: `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`. Source: https://developers.circle.com/stablecoins/usdc-contract-addresses (fetched 2026-11-23). Chain id 8453 (confirmed with `cast chain-id --rpc-url https://mainnet.base.org`). On-chain `name()` = `"USD Coin"`, `version()` = `"2"` (read with `cast call` against https://mainnet.base.org on 2026-11-23). `DOMAIN_SEPARATOR()` = `0x02fa7265e7c5d81118673727957699e4d68f74cd74b7db77da710fe8a2c7834f` at read time.
- Base Sepolia USDC: `0x036CbD53842c5426634e7929541eC2318f3dCF7e`. Chain id 84532 (confirmed with `cast chain-id --rpc-url https://sepolia.base.org`). On-chain `name()` = `"USDC"`, `version()` = `"2"` (read via https://sepolia.base.org on 2026-11-23).
- Therefore the EIP-712 domain for the signature is `{ name, version: "2", chainId, verifyingContract }` with name `"USD Coin"` on Base mainnet and `"USDC"` on Base Sepolia. The safe rule is to take `name` and `version` from `PaymentRequirements.extra` and verify them against `name()`/`version()` on the token before signing, or to keep a per-chain table pinned in banda's code.
- Note: the Circle page does not state the EIP-712 domain. The on-chain read is the evidence.

### Security literature
- arXiv 2605.30998 "Free-Riding in the AI Economy: Demystifying Logic Flaws in x402-Enabled Payment Systems", submitted 2026-05-29. Source: https://arxiv.org/html/2605.30998v1 (fetched 2026-11-23). Study scope: four official SDKs (TypeScript, Python, Java, Go); front-running tests on 8 networks. Reported classes (the reader's summary, not verified against the paper's own counting): (a) settlement TOCTOU front-running (theoretical; failed against the official SDK, which waits for confirmation); (b) cross-resource substitution, where a payment for one resource unlocked another in 100 of 100 trials (server-side matching, TypeScript and Python incomplete matching, Java checks unsigned metadata, Go trusts the facilitator blindly); (c) probabilistic service duplication (3 of 50 rounds) with no nonce locking on server or facilitator; (d) allowance overdraft in the `upto` scheme (97.76% of value unpaid in a 50-request burst); (e) long-context variant of overdraft; (f) facilitator denial of settlement under rate limiting (86.95% leakage at 50 rps against a 10 rps limit).
- A secondary guide (https://ledgers.ae/protocols/x402/) says the same study found 11 vulnerabilities. The arXiv abstract and the fetched summary do not confirm 11, so the count is unverified.
- USENIX Security '26 has a related session "When HTTP 402 Meets the Blockchain: Risks on Emerging x402 Payments" (https://www.usenix.org/conference/usenixsecurity26/technical-sessions). Its abstract describes facilitator-held asset theft and unbounded sponsor-paid gas. I did not read the paper.
- NDSS 2026 poster on a two-phase gap in x402 (https://www.ndss-symposium.org/wp-content/uploads/ndss26-poster-51.pdf). Not read in full.

## Recommendations (for banda's design)

1. Pin the v2 line: `@x402/core`, `@x402/evm`, `@x402/fetch` at exact 2.32.0. Keep the client as the payer and do not run a resource server in the wallet code path. Pin `viem` at exact 2.58.4.
2. Build the EIP-712 domain from a per-chain table pinned in code, with `name` `"USD Coin"` for Base mainnet (8453) and `"USDC"` for Base Sepolia (84532), `version` `"2"`, and `verifyingContract` taken from the table. At signing time, compare `PaymentRequirements.extra.name` and `version` to the table and refuse on mismatch.
3. Before signing, check the challenge client-side: `network` is one of the configured CAIP-2 ids; `asset` equals the pinned USDC address for that chain; `payTo` is not blank and its recipient rule (Always, Ask, Deny) is resolved; `amount` is within the wallet balance; `maxTimeoutSeconds` yields a `validBefore` that is short (for example, under 10 minutes). Never sign a requirement that fails any check.
4. Never let the server's 402 choose the recipient silently. The recipient approval rule (per address or x402 endpoint) is the authoritative check, as the owner requested; the challenge `payTo` must match the approved address.
5. Use a random 32-byte nonce per authorization (`crypto.getRandomValues`), and persist each signed nonce in the store before the request is sent, so a crash cannot lead to a second signature for the same intent; use the store as the single source of truth (principle 1 in AGENTS.md).
6. Treat the facilitator's `settlement_pending` as a non-final state: record the tx hash, then reconcile by reading the chain, not by retrying the payment.
7. Do not retry a paid request blindly. A retry after `PAYMENT-RESPONSE` failure must generate a new nonce and a new authorization.
8. Prefer v2 (`PAYMENT-*` headers, CAIP-2). Support v1 only if a required endpoint speaks only v1; then isolate the v1 path behind a flag.
9. Add fault tests for: duplicate challenge; challenge with a wrong `asset` or chain; signature with stale `validBefore`; crash between nonce persist and send; facilitator returning `settlement_pending`.

## Open questions

1. Whether the repo's reference facilitator is a separate package or a hosted service only (the `@x402/facilitator` name does not exist on npm). Confirm which facilitator banda will call and whether it is trusted to settle without a banda-side check.
2. The exact EIP-712 domain of the USDC `version` after any future USDC upgrade; re-read on-chain before shipping.
3. Whether the EIP-3009 `receiveWithAuthorization` path is needed for any banda flow (only relevant if banda ever acts as a payee).
4. The true vulnerability count in arXiv 2605.30998 (the secondary guide says 11; the fetched text supports six classes with sub-patterns). Read the full paper before citing a number.
5. Whether `coinbase/x402` and `x402-foundation/x402` are both canonical. Both appear as repository URLs on npm; pick one and pin it in the design.
